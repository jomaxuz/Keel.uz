## Optimizatsiya rejasi (ertaga)

### P1 — Public GET javoblarini siqish (gzip/br) 🟢 eng oson, katta yutuq
- Hozir `/api/v1/restaurant` (22 KB), `/menu`, `/categories` **siqilmasdan**
  ketyapti. Caddy'да `encode zstd gzip` yoqilsa payload ~5–7 barobar kichrayadi
  → caddy CPU, bandwidth va mobil yuklanish vaqti bir vaqtda tushadi.
- **Qadam:** Caddyfile'га (yoki nginx pagecache'ga) `encode` qo'shish, `_test`
  bilan `content-encoding: gzip` chiqishini tekshirish.

### P2 — Public GET'larni keshlash 🟢 eng katta yutuq (mongo yukini oladi)
Har foydalanuvchi oqimida ~9 request'dan **5 tasi** kamdan-kam o'zgaradigan GET
(restaurant, menu, categories, promotions, payment-methods). Ular hozir **har
safar mongoga** boradi.
- `cache-control: public, max-age=30..60` qo'shib, pagecache (nginx) yoki
  caddy'да qisqa TTL bilan tenant+path bo'yicha keshlash.
- ⚠️ **Kesh invalidatsiyasi**: admin menyuni/profilni o'zgartirganda kesh
  tozalanishi kerak (yoki qisqa TTL — 30–60 s — bilan o'zi eskiradi). Qisqa TTL
  xavfsizroq boshlanishi.
- Bu **shiftni bir necha barobar** oshiradi: o'qishlar mongoga yetib ham
  bormaydi.

### P3 — Mongo indekslari va slow-query profiling 🟡
- Slow-query profiling'ни qisqa yoqish: `db.setProfilingLevel(1, {slowms: 50})`,
  yukни qayta berib, `db.system.profile` dan indekssiz so'rovlarni topish, keyin
  o'chirish.
- Hot handler'lar (`GetMenu`, `GetRestaurant`, `GetCategories`, `GetPromotions`,
  `DeliveryQuote`) so'rovlarini `.explain()` bilan tekshirish — `COLLSCAN` bo'lsa
  indeks qo'shish.
- P2 (kesh) qilingandan keyin bu ikkinchi darajaga tushadi, lekin uzoq muddatga
  kerak.

### P4 — Caddy TLS optimizatsiyasi 🟡
- TLS session resumption / tickets yoqilganini tekshirish (handshake CPU'ni
  kamaytiradi).
- HTTP/2 keep-alive — brauzer ulanishni qayta ishlatsin, har request'ga yangi
  handshake bo'lmasin.
- OCSP stapling keshlanganini tekshirish.

### P5 — OS / ulimit 🟡
- Serverда `ulimit -n` = **1024** (past). Yuqori parallellik uchun host va
  konteynerlar uchun 65535 ga ko'tarish.
- Har backend'ning mongo connection pool o'lchamini ko'rib chiqish.

### P6 — Kelajak uchun (o'sish bo'lganda) ⚪
- **Mongo'ni alohida qutiga** yoki managed'ga chiqarish — 4-yadroli qutining eng
  katta iste'molchisini bo'shatadi. Birinchi arxitektura o'zgarishi shu bo'lishi
  kerak.
- Yoki vertikal: 8 vCPU. Hozir **shart emas** — 12 tenant real yuki juda kichik,
  server katta zaxira bilan turibdi.

### P7 — Kelgusi test uchun 🔵
- Aniq shiftни o'lchash uchun keyingi testда generatorni **o'sha data-markazdagi
  ikkinchi VPS'дан** yuritish (bu testда generator server bilan yadro talashdi).
- Serverга yengil metrics endpoint / mongo slow log qo'shib, keyingi test
  ichkaridan aniq o'lchansin.
